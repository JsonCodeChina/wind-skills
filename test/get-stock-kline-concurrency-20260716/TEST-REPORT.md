## 测试方法

1. 每个请求启动一个独立 Node.js CLI 进程。
2. 同一档位的所有请求同时启动，通过 `Promise.all` 等待全部完成。
3. 不同请求使用不同 A 股标准 Wind 代码，最大档位覆盖 20 只股票。
4. 每个请求记录退出码、耗时、错误码、后端返回代码、行数和日期范围。
5. 调度器超时为 660 秒，本次没有请求触发调度器超时。

## 失败分析

### `NETWORK_ERROR`

两轮 10 并发共出现 4 次：

- 第一轮：`300750.SZ`、`600036.SH`
- 第二轮：`600036.SH`、`600900.SH`
- 第二轮 detail：`fetch failed (server=stock_data)`
- 耗时约 11 秒
- 错误信封正确标记：允许原样重试 1 次

`600036.SH` 在两轮 10 并发中都失败，但在 5 并发和 20 并发阶段成功，因此不是标的或参数问题，而是并发期间的连接/后端瞬时失败。

### 修复前：后端并发超限被错分为 `UNKNOWN`

第二轮 20 并发中，`002415.SZ` 和 `600887.SH` 返回：

```text
当前工具并发请求数量超限，请稍后重试
```

但 CLI 输出为：

```json
{
  "code": "UNKNOWN",
  "retry": {
    "allowed": false,
    "mode": "after_correction",
    "max_attempts": 0
  }
}
```

这是本次测试发现的明确错误分类缺陷（后续已修复）：

- 该错误属于并发/频率限制，不应是 `UNKNOWN`。
- 应映射为 `RATE_LIMIT_ERROR` 或独立的 `CONCURRENCY_LIMIT_ERROR`。
- 应允许等待后原样重试一次，不应标记为不可重试。
- 外层调度器应立即降低并发度，不要继续同级别批量请求。

第一轮 20 并发还有 1 个 `UNKNOWN`（`000725.SZ`），由于第一轮脚本尚未保存 detail，无法确认是否为同一后端并发超限原文。

### 修复后真实复测

新增专用错误码 `CONCURRENCY_LIMIT_ERROR` 后，又执行了两轮三档真实并发复测，原始证据为：

- `raw-results-after-fix.json`
- `raw-results-after-fix2.json`

复测中 20 并发多次触发后端原文“当前工具并发请求数量超限，请稍后重试”，所有该类错误均正确返回：

```json
{
  "code": "CONCURRENCY_LIMIT_ERROR",
  "retry": {
    "allowed": true,
    "mode": "same_request_after_wait",
    "max_attempts": 1,
    "after_ms": 3000
  },
  "circuit_breaker": {
    "tripped": true,
    "scope": "remaining_batch",
    "action": "abort_remaining_calls"
  },
  "correction": {
    "strategy": "reduce_concurrency",
    "change_only": ["concurrency"],
    "recommended_max_concurrency": 5,
    "preserve_server_type": true,
    "preserve_tool_name": true,
    "preserve_params": true
  }
}
```

复测结论：

- 并发超限不再归类为 `UNKNOWN`。
- 不再错误地标记为不可重试。
- 会熔断剩余批次，要求外层调度降低并发。
- 重试保留原 `server_type`、`tool_name` 和业务参数，只允许调整并发度。

### 50 并发错误验证

50 并发的 14 个失败中：

- 13 个后端并发超限全部正确分类为 `CONCURRENCY_LIMIT_ERROR`。
- 这 13 个错误均允许等待 3 秒后原样重试一次。
- 这 13 个错误均触发 `remaining_batch` 熔断。
- 这 13 个错误在当时版本均要求将并发度降至 5，保留路由和业务参数；当前策略已调整为默认恢复串行，显式并发最多 10。
- 1 个 `NETWORK_ERROR` 正确标记为允许原样重试一次。
- 未出现 `UNKNOWN`。

### 50 并发数据一致性

- 日期全部位于 `20260701` - `20260715`。

### 50 并发结论

50 并发不适合直接用于生产：

- 错误分类、重试、熔断和降并发指令均按修复后的契约生效。

## 结论与建议

### 生产调用策略

Skill 当前策略为默认串行（并发数 **1**），不主动发起并发请求。只有用户明确要求并发时才允许并发，硬上限为 **10**，超过 10 的请求排队分批执行。

测试样本表明，并发数 5 是显式开启并发后的保守档位：

- 两轮 10/10 全部成功。
- P95 为 1.57 - 2.16 秒。
- 没有触发网络错误或后端并发上限。

不建议直接使用 20 并发，因为已经确认后端并发超限。10 并发在本次两轮测试中成功率仅 80%，因此只是允许的最大值，不是默认值。

### 建议调度策略

1. 默认串行执行 `get_stock_kline`；用户明确要求并发时最多同时执行 10 个，超出的请求排队。
2. 其余标的排队，上一个任务完成后再启动下一个。
3. `NETWORK_ERROR` 按现有错误信封原样重试最多 1 次，建议加 1-3 秒随机抖动。
4. 收到“当前工具并发请求数量超限”时立即暂停发起新请求，等待后从更低并发度继续。
5. 已新增 `CONCURRENCY_LIMIT_ERROR` 并通过真实 20 并发复测；调度器应直接执行该错误的 `retry/circuit_breaker/correction`。
