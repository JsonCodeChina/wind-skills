## 4. 逐项分析

### 4.1 并发上限与并发超限

#### 修改前

修改前的 `SKILL.md` 没有明确的统一并发上限，也没有首项探针规则。多个标的通常拆成多次调用，但调度器可能一次性并发启动，超过后端上限时表现为并发超限或网络类错误。

#### 修改后

当前版本增加了两层约束：

1. 默认并发数为 1；
2. 只有用户明确要求并发时才允许并发，最大并发数为 10；
3. 超过 10 的请求必须排队分批；
4. 批量调用先执行第一个请求作为探针；
5. `CONCURRENCY_LIMIT_ERROR` 会中止剩余批次，等待后恢复串行。

CLI 同时将“并发请求数量超限”等后端文本识别为独立的 `CONCURRENCY_LIMIT_ERROR`，避免误归类为普通网络错误。

#### 判定

**在 Skill 调度层已经解决。** 需要注意，后端最大并发 10 的限制并未消失；直接绕过 Skill、从多个进程并发调用 CLI 时，CLI 本身没有全局信号量，仍可能触发后端限制。

### 4.2 港股、美股描述合并

#### 修改前

修改前已经在总范围中写明 A 股、港股、美股都使用 `stock_data`，但契约集中在单一 `tool-contracts.md`，领域边界与工具查找成本较高。

#### 修改后

当前版本进一步统一为：

- `stock_data` 同时覆盖 A 股、港股和美股；
- 三个市场共用 `references/stock.md`；
- 港股、美股不再维护独立 Skill 路由；
- 交易所代码和自然语言名称均交给同一 CLI 归一化入口。

#### 判定

**已解决。** 但“共用股票服务”不等于每一个股票工具都覆盖三个市场。例如当前 `get_stock_fundamentals` 契约仍明确仅支持 A 股财务数据，路由时仍应遵守具体工具契约。

### 4.3 日期格式和日期字段

#### 修改前

修改前直接暴露三套后端字段：

- K 线：`begin_date/end_date`；
- Quote：`begin/end`；
- EDB：`beginDate/endDate`。

文档主要要求 `yyyyMMdd`，同时部分参考文件又声明兼容 `yyyy-MM-dd` 和其它格式，容易造成调用方选择不一致。

#### 修改后

公共契约统一为：

- 字段：`begin_date/end_date`；
- 格式：`yyyy-MM-dd`；
- 禁止 `LAST`、`yyyyMMdd` 和隐式日期。

CLI 根据工具自动映射：

| 工具类型 | 公共字段 | 后端字段 |
| --- | --- | --- |
| K 线 | `begin_date/end_date` | `begin_date/end_date` |
| Quote | `begin_date/end_date` | `begin/end` |
| EDB | `begin_date/end_date` | `beginDate/endDate` |

同时将日期值从 `yyyy-MM-dd` 转成后端需要的 `yyyyMMdd`。

针对性验证结果：

```text
K线：2026-07-01 → begin_date=20260701
Quote：begin_date → begin=20260717
EDB：begin_date → beginDate=20250101
```

#### 判定

**已解决。** 后端仍然存在三套字段，但差异已被封装在 CLI 内，不再暴露给 Skill 调用方。

### 4.4 总市值口径

#### 修改前

修改前的部分参考文件已经记录：

- `总市值1`：不含限售股；
- `总市值2`：含限售股；

但同时存在把无后缀“总市值”自动映射到 `总市值2` 的归一化规则，容易在用户口径不明确时静默选错。

#### 修改后

当前 `stock.md` 和 CLI 契约前言统一规定：

- `总市值1` = 不含限售股；
- `总市值2` = 含限售股；
- 用户只说“总市值”时先确认口径；
- 指标必须从当前领域契约逐字选择，不再静默使用旧别名表推断。

#### 判定

**已解决。** 解决重点不是合并两个字段，而是保留两个口径并禁止在语义不明确时自动代选。

### 4.5 `lang` 参数

#### 修改前

修改前对调用方暴露了两套后端枚举：

- 股票、基金、指数、债券等使用 `中文/English`；
- Analytics 使用 `CNS/ENS`；
- 部分兼容规则又接受 `zh-CN/en-US`。

#### 修改后

公共参数统一为：

- `zh-CN`；
- `en-US`；
- 默认 `zh-CN`。

CLI 在调用前转换：

| 服务 | 公共值 | 后端值 |
| --- | --- | --- |
| 股票、基金、指数、债券等 | `zh-CN/en-US` | `中文/English` |
| Analytics | `zh-CN/en-US` | `CNS/ENS` |

针对性验证中，Analytics 的 `en-US` 被正确转换为 `ENS`。

#### 判定

**已解决。**

### 4.6 `question/query` 参数

#### 修改前

23 个自然语言工具使用 `question`，两个金融文档工具使用 `query`。调用方必须根据工具记忆不同字段。

#### 修改后

公共契约统一使用 `question`。CLI 对以下工具自动转换：

- `get_company_announcements`：`question → query`；
- `get_financial_news`：`question → query`。

若调用方同时传入 `question` 和 `query` 且值不同，CLI 会返回参数冲突错误，不会静默覆盖。

针对性验证中：

```text
{"question":"贵州茅台新闻"}
→
{"query":"贵州茅台新闻"}
```

#### 判定

**已解决。**

### 4.7 NER 报错重试

#### 修改前

修改前已有 `MARKET_TARGET_NOT_FOUND` 文案，但主要依赖 agent 阅读长文本执行，批量请求也缺少明确的首项探针和全批次阻断机制。

#### 修改后

当前版本：

- 将 NER 相关文本独立识别为 `MARKET_TARGET_NOT_FOUND`；
- 不允许任意猜测交易所后缀；
- 中文名称优先要求更明确的名称或 Wind 标准代码；
- 仅在明确美股语境且原输入是裸 ticker 时，允许补 `.O` 重试一次；
- NER 失败触发剩余批次熔断；
- 重试保持原 `server_type` 和 `tool_name`；
- 二次失败后要求用户提供准确全称或 Wind 标准代码。

#### 判定

**已解决。** 当前规则避免了 NER 失败后跨工具、跨市场或无限猜测代码重试。

### 4.8 错误响应体和错误引导

#### 修改前

修改前已有基础的 `error.code` 和 `agent_action`，但错误策略主要是文本形式，且部分后端原始错误可能直接暴露，无法稳定提供统一的重试、熔断和修正字段。

#### 修改后

所有失败统一为：

```json
{
  "ok": false,
  "error": {
    "code": "...",
    "message": "...",
    "details": {
      "server_type": "...",
      "tool_name": "...",
      "backend_error": {}
    },
    "retry": {},
    "circuit_breaker": {},
    "correction": {},
    "agent_action": "..."
  }
}
```

当前版本还区分认证、日额度、余额、QPS、并发、网络、NER、参数、无结果和未知错误。后端原始错误保留在 `details.backend_error`，但不会绕过统一错误信封。

#### 判定

**已解决。**

### 4.9 多个 `windcode`

#### 修改前

修改前 `SKILL.md` 明确施加全局单标的限制：

- `windcode` 只能是单个字符串；
- 禁止数组、逗号拼接和多代码字符串；
- 多标的必须拆分为多次调用。

但修改前的 `parameter-conventions.md` 又写有“以工具契约和后端实际支持为准”，存在内部冲突。

#### 修改后

当前版本取消全局单标的限制，改为：

> `windcode` 的类型和多标的传入方式以当前工具契约为准。

CLI 对 `600519.SH,000001.SZ` 这样的字符串不会报本地参数错误，也不会擅自拆分或改写。

#### 判定

**部分解决。** 已完成的部分是移除错误的全局禁令，允许后端具备批量能力的工具接收多代码字符串。尚未完成的部分是：

- 各 `windcode` 工具契约仍普遍写成单个“股票名称或者股票代码”；
- 没有逐工具说明使用逗号字符串还是数组；
- 没有声明批量数量上限；
- 没有真实回归证明所有 Quote、K 线和价格指标工具都支持相同的批量格式。

因此当前不能笼统宣称“全部工具都支持多代码”。建议建立逐工具能力表，并为支持批量的工具补充格式、上限和真实测试。

### 4.10 `period` 魔法数字

#### 修改前

后端 K 线周期使用数字编码，调用方容易直接传 `10`、`11` 等不可读的魔法数字；文档和运行时对公共值、后端值的边界不够严格。

#### 修改后

公共契约只允许语义周期：

```text
1min, 5min, 10min, 15min, 30min, 60min, 120min,
240min, 1d, 1w, 1mo, 1y, 1q, 6mo
```

CLI 通过 `kline_period_map` 转换成后端数字，例如：

- `1d → 10`；
- `1w → 11`；
- `1mo → 12`。

如果调用方直接传后端数字，CLI 会按非法公共枚举处理，而不是继续传播魔法数字。

#### 判定

**已解决。**

## 5. 架构层面的主要变化

修改前采用：

```text
SKILL.md
  → tool-contracts.md
  → indicators.md
  → 多份 normalization / validation / error JSON
  → cli.mjs
```

修改后采用：

```text
SKILL.md
  → 按领域读取一份 references/{domain}.md
  → call-rules.json 完成公共参数到后端参数的映射
  → cli.mjs 统一校验、调用、结果和错误信封
```

改进效果：

1. 每次只读取一个领域契约，降低路由时的上下文量；
2. 指标字典嵌入股票、基金、指数领域契约，减少跨文件查找；
3. 公共参数与后端参数明确分层；
4. 错误策略从纯文本建议升级为机器可读策略；
5. 回归测试覆盖契约同步、日期、语言、字段映射、NER、并发和错误信封。

## 6. 后续建议

### 高优先级

1. 为每个含 `windcode` 的工具增加批量能力声明：
   - 是否支持多代码；
   - 参数类型；
   - 分隔格式；
   - 最大代码数；
   - 返回结果是否保序。
2. 增加多代码真实回归测试，至少覆盖股票、基金、指数的 Quote、K 线和价格指标工具。

### 中优先级

3. 如需保证多个外部进程也不超过并发 10，应增加跨进程信号量或集中调用队列；仅依赖 Skill 文档无法约束绕过 Skill 的直接调用。
4. 将本次 10 类问题做成固定的契约回归测试，避免后续同步后端契约时回退。

## 7. 最终结论

当前版本已实质解决日期、语言、自然语言字段、市值口径、NER 重试、错误引导和 K 线周期等核心一致性问题；港美股也已统一进入股票领域契约。

需要保留两个限定：

- 并发问题通过调用调度规则规避，后端的并发上限仍然存在；
- 多 `windcode` 已从“全局禁止”改为“按工具能力处理”，但批量能力尚未逐工具完成契约化和真实验证。

因此，准确结论是：**8 项完整整改完成，1 项在 Skill 调度范围内完成，1 项部分完成。**
