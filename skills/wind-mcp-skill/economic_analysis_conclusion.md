# 新版 EDB 工具使用习惯分析结论

> 数据源：`economic_analysis.csv`（近 24 小时调用日志）
> 时间跨度：2026-08-30 10:23 → 2026-08-31 10:23（正好 24h）
> 样本量：**4924 次调用**，**420 个去重用户**，仅涉及 `economic_data` 的两个工具

---

## 一、总体分布

| 工具 | 调用数 | 占比 | 定位 |
| --- | --- | --- | --- |
| `query_economic_indicator_data` | 3667 | 74.5% | 取时间序列数值（支持自然语言 **或** 代码直传） |
| `search_economic_indicator` | 1257 | 25.5% | 找指标 / 确认代码，**不取数** |

`query` 提问方式构成（n=3667）：

- **纯代码直传**（`M0075992` 式）：2450 次，**66.8%** —— 最高效
- **自然语言直传**（无代码、无前置 search）：1217 次，**33.2%** —— 证明 query 不依赖 search 也能取数
- 时间参数合规性极好：只有 **21 次（0.6%）** 同时缺 `beginDate/endDate` 和 `observation`（会被后端拒）。「必须给时间范围」这条引导是生效的。

---

## 二、核心结论（先说结论）

1. **用户的猜想成立，但只是次要问题**：确有「先 search 再 query」的冗余，但占比不大——真正冗余（search 后又用自然语言 query 同一个指标）约 **100 次**，其中 41 次是字面上「搜了 X 再按名字查 X」的纯浪费。

2. **更大的浪费是「重复重试」而非「多余 search」**：**572 次**调用是对**完全相同**入参的连续重复（占全部调用的 11.6%、占 query 的 15.6%），远超 search 冗余。这违反了 SKILL 里「不得原样重发相同调用」的规则，是当前最该修的引导缺口。

3. **search 被过度用于「确认已知指标的代码」**：89% 的 search 是针对一个**具体已命名指标**（而非探索「有哪些」），48%（608 次）是无代码的单一/双指标名称。对 CPI、PMI、GDP、LPR、主要汇率这类**常见且唯一**的指标，完全可以直接 query 自然语言，search 纯属多一跳。

4. **近一半 search 是「死胡同」**：1257 次 search 中，**557 次（44.3%）** 在 5 分钟内没有跟进任何 query（其中 355 次只是接着又 search，202 次之后什么都没做）。search 的探索价值真正被用到的场景（探索型「有哪些/相关」）只占 **10.8%**。

## 三、分项证据

### 3.1 search 的去向（1257 次，5 分钟窗口内按同一用户完整划分）

| search 之后发生了什么 | 次数 | 占比 | 判读 |
| --- | --- | --- | --- |
| → 最终用**代码** query（预期的「确认代码」流程） | 600 | 47.7% | 合理，但对常见指标可省 |
| → 只是继续 search，没取数 | 355 | 28.2% | churn，指标探索空转 |
| → 之后什么都没做 | 202 | 16.1% | 死胡同 search |
| → 用**自然语言** query（**search 本可省略**） | 100 | 8.0% | **冗余** |

> 「search 从未导向取数」= 355 + 202 = **557 次（44.3%）**。

### 3.2 冗余 search 的实锤样例（搜完再按同名查，overlap≥0.6 共 41 例）

```
search: 中国制造业PMI月度数据            =>  query: 中国制造业PMI
search: 美国核心PCE物价指数              =>  query: 美国核心PCE物价指数
search: 美国核心CPI同比                 =>  query: 美国核心CPI同比
search: 中国贷款市场报价利率LPR 1年期和5年期以上 =>  query: 贷款市场报价利率LPR 1年期和5年期以上
search: 美元兑日元                      =>  query: 美元兑日元（日度）
search: 碳酸锂价格                      =>  query: 中国:价格:碳酸锂(电池级,99.5%,国产)
```

这些指标名称唯一、无歧义，`query` 传自然语言能直接命中，前置 search 只增加一次调用和一次等待。

### 3.3 重复重试（最大浪费项）

- **635 次** query 是同一用户在 120 秒内对**完全相同**入参的重发（占 query 的 17.3%）。
- 连续 ≥3 次相同 query 的「重试串」共 58 段，累计 **572 次**多余重发。
- query 入参去重率 **35.2%**（3667 次 → 仅 2377 个不同入参）；search 仅 8.9%，说明重试问题几乎全在 query 侧。

最严重的几例：

| 用户 | 重复入参 | 连续次数 | 时间跨度 |
| --- | --- | --- | --- |
| 142754693 | `M0075992` | **206 次** | 约 55 分钟 |
| 144362983 | `M0066367` | 25 次 | 110 秒 |
| 144362983 | `S0213050,M0066367,S0213049,Y4998629` | 24 次 | 80 秒 |
| 144362983 | `Z1582998` / `M1001791` / `G0001680` … | 各 24 次 | ~76 秒 |
| 142776049 | `G1100004` | 10 次 | 约 5.8 小时 |

单个用户对同一代码重发 206 次，是明显的失控循环（大概率首个调用报错/超时后无限重试），而非正常需求。

### 3.4 引导已经生效的部分（无需改）

- 时间参数缺失率仅 0.6%，「query 必须带 `beginDate/endDate` 或 `observation`」这条约束执行到位。
- 66.8% 的 query 直接用代码、33.2% 直接用自然语言——大多数用户已经在走「直接 query」的高效路径。
- 把时间硬塞进 `question` 的只有 50 次，属边角。

## 四、引导问题诊断

| 症状 | 数据 | 根因（引导层面） | 严重度 |
| --- | --- | --- | --- |
| 相同调用无限重试 | 572 次多余重发；单用户 206 次 | 「不得原样重发」约束不够显眼、没有硬性「相同(tool+args)不得重复」红线 | 🔴 高 |
| 常见指标也先 search 再 query | 100 次纯冗余 + 600 次「确认代码」中相当一部分可省 | 没讲清「什么时候**不需要** search」；把 search 当成 query 的默认前置 | 🟡 中 |
| search 空转、不落到取数 | 557 次（44.3%）search 无跟进 | 探索型与确认型没区分，探索完缺少「拿到代码后直接 query」的收口指引 | 🟡 中 |

---

## 五、改进建议（针对 `references/economic.md` 与 `SKILL.md`）

1. **加一条硬红线止血重试**（收益最大）：
   > 同一 `tool_name + arguments` 的调用不得重复发出。上一次成功即直接用结果；上一次报错，必须先按错误信息**改参数或换工具**，否则停止并向用户说明——严禁原样重发。连续两次相同入参即视为异常，立即中止。

2. **明确「无需 search」的场景，给正例**：
   > 指标名称常见且唯一（CPI、PMI、GDP、社融、LPR、主要汇率、主流商品价格等）时，**直接** `query_economic_indicator_data` 传自然语言，不要先 search。`search` 仅用于：① 不确定指标是否存在或口径；② 一个描述可能对应多个候选、需先挑代码；③ 用户明确要「有哪些/相关指标」的清单。

3. **给 search→query 一个收口动作**：
   > `search` 命中后，若已确认目标指标，**下一步直接用返回的 `code` 调用 query 取数**；不要再用自然语言重查一遍，也不要连续多次 search。

4.（可选）**观测期上限提示**：有 28 次 `observation=5000` 式的超大取数，建议在契约里提示合理上限，避免一次拉全历史。

---

## 六、一句话总结

引导确有可优化空间，但**优先级要摆正**：先补「禁止相同调用重试」的硬约束（省下约 570 次/24h 的空转），再补「常见指标直接 query、不必先 search」的正例（省下约 100+ 次冗余 search）。当前 2/3 的 query 已走高效代码直传、时间参数合规率 99.4%，说明主干引导是健康的，问题集中在**重试失控**和**search 的过度前置**两点。
